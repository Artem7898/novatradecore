# Модернизация и границы результата

Изменения выполняются в порядке: защита действующего API → финансовый контракт → воспроизводимые проверки → архитектура и эксплуатация → измерения. Документ описывает состав изменений и действия владельца инфраструктуры; наличие конфигурации CI не означает успешного production-развёртывания.

## Что вводится в коде

| Область | Изменение | Проверка |
|---|---|---|
| API | Сервисные Bearer-токены, общий rate limit и read-only Trade admin | Auth/rate-limit regression tests; Redis integration |
| Денежные данные | Единая схема, конечные положительные Decimal, precision/scale, notional и валюта котировки | Граничные и property-based tests; DB constraints |
| Повторы | Уникальный ключ биржи и события, идентичный replay и конфликт | PostgreSQL integration tests |
| Слои | HTTP-адаптер, application service, чистая логика расчётов, ORM persistence | Сервисные и endpoint tests |
| Зависимости | Поддерживаемая Django LTS, удаление неподключённого Nova-концепта, uv lock | Frozen install, dependency audit, wheel build |
| Качество | Ruff, Pyright, pre-commit и CI | Проверки ветки на Python 3.12/3.13 |
| Доставка | Раздельные dev/prod Compose и роли БД, непривилегированный образ, health endpoints, отдельный release шаг | Container build, smoke checks, migration checks |
| Измерения | Аутентифицированный benchmark без обещаний throughput | Артефакты прогона с ошибками, задержками и параметрами |

## Изменения контракта для клиентов

- Цена и количество принимаются только как валидные десятичные строки; ранее допускавшиеся ошибочные значения будут отклоняться.
- API требует Bearer-токен. Клиенты должны обрабатывать 401/429/503 и ограничивать повторы.
- `notional` обозначает стоимость сделки; новое API не возвращает legacy `pnl`.
- Повтор одного события возвращает 200; новый event — 201; изменение данных под существующим ключом — 409.
- Идентификатор события уникален в пределах `exchange_id`, а не между всеми биржами.
- Котировки ограничены USD/USDT/USDC с номинальным допущением 1:1. Для других валют нужен отдельный контракт.

Обновление схемы требует предварительного аудита существующих данных, backup, репетиции на копии и остановки ingestion во всех старых экземплярах до миграции `0003`. Ограничения миграции и downgrade описаны в [runbook](operations.md#миграция-legacy-данных).

## Действия вне исходного кода

Владелец репозитория и окружения должен:

1. Просмотреть изменения и результаты CI, затем выбрать момент merge и release.
2. Включить защиту основной ветки с обязательными проверками CI и review. Workflow в репозитории не меняет правила GitHub автоматически.
3. Задать реальные секреты, разрешённые хосты, сетевые ограничения и доверенную конфигурацию reverse proxy/TLS; подготовить runtime/release роли на существующей БД.
4. Подготовить backup/restore, окно миграции и процедуру отката; проверить её на копии данных.
5. Настроить сбор логов и метрик, уведомления о 5xx, недоступности зависимостей и росте задержек. Grafana не считается автоматически настроенной.
6. Повторить нагрузочные измерения на целевой конфигурации и установить свои критерии успешных RPS, error budget и p95/p99.

## Решения после измерений

`src-layout` не является необходимым условием исправления приложения; текущая Django-структура сохраняется. Переход имеет смысл при ясной задаче упаковки или границ импортов.

Брокер сообщений и фоновые workers добавляются при необходимости durable очереди, повторной обработки и backpressure. Перед этим нужно определить гарантии доставки и идемпотентность; сам брокер не исправляет неверные денежные данные.

Connection pooling, COPY/batching, партиционирование и новые индексы выбираются по измерениям соединений, I/O, планов запросов и профилю данных. Проверка сборки не подтверждает нулевой простой или HFT-ready статус. Для тяжёлых вычислений требуется отдельное профилирование CPU и влияния на event loop.
