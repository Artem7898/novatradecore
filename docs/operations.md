# Эксплуатация

## Границы сервиса

NovaTradeCore принимает события от доверенных сервисных клиентов. Токен даёт право ingestion; это не пользовательская сессия и не полная система управления ролями. Авторизация применяется к действующему Django-маршруту. Rate limit считает запросы на настроенное имя клиента, поэтому ротация секрета без смены имени не должна использоваться для обхода квоты.

Redis в production хранит общие счётчики ограничения запросов. Его недоступность приводит к отказу ingestion с 503. Это не durable очередь: остановка/очистка Redis теряет текущие счётчики, но не сделки в PostgreSQL. Не открывайте Redis внешним клиентам и не очищайте production-кэш для решения ошибок API.

`USD`, `USDT` и `USDC` поддерживаются с явно заданным номинальным допущением 1:1. При необходимости FX-курса или оценки depeg требуется отдельная модель котировок. `notional` не означает P&L. Оценка риска является набором детерминированных правил, а не моделью AML или инвестиционной рекомендацией.

## Production-конфигурация

Создайте `.env` на целевом сервере из `.env.example`, задав собственные значения. `make init` предназначен для генерации конфигурации разработки. Production требует:

| Переменная | Назначение |
|---|---|
| `SECRET_KEY` | Случайный Django secret длиной не менее 50 символов |
| `ALLOWED_HOSTS` | Явный список имён хостов без `*` |
| `INGEST_API_TOKENS` | JSON-объект `{ "client-name": "random-service-secret" }`; каждый секрет не короче 32 символов |
| `DATABASE_NAME`, `DATABASE_USER`, `DATABASE_PASSWORD` | Отдельная БД и runtime-роль приложения с DML-правами; пароль не короче 32 символов |
| `MIGRATION_DATABASE_USER`, `MIGRATION_DATABASE_PASSWORD` | Отдельная роль release-процесса, владеющая таблицами; без SUPERUSER, пароль не короче 32 символов |
| `POSTGRES_ADMIN_PASSWORD` | Bootstrap-пароль роли PostgreSQL `postgres`; не передаётся web-процессу |
| `DATABASE_HOST`, `DATABASE_PORT` | Адрес PostgreSQL из сети приложения |
| `REDIS_URL`, `REDIS_PASSWORD` | Общий Redis и его непубличные учётные данные |
| `INGEST_RATE_LIMIT`, `INGEST_RATE_WINDOW_SECONDS` | Квота клиента; по умолчанию 300 запросов за 60 секунд |
| `TRUST_PROXY_HEADERS` | По умолчанию `false`; включайте только для доверенного TLS ingress |
| `APP_IMAGE_TAG` | Уникальный тег release; для воспроизводимых обновлений не переиспользуйте его |

Защитите `.env` правами доступа и используйте secret manager, если он есть в инфраструктуре. Не включайте ключи и пароли в Git, access logs, трассировки и benchmark metadata.

Статические файлы `/static/` обслуживаются reverse proxy или отдельным static server: предоставьте ему read-only доступ к результату `collectstatic` (например, к тому `static_data` в Compose). Uvicorn с production-настройками не раздаёт эти файлы.

TLS завершается на reverse proxy. Только этот proxy должен иметь доступ к HTTP-порту приложения. Доверие `X-Forwarded-Proto` включайте лишь при удалении клиентских forwarded-заголовков на proxy и установке им проверенного значения. Без этого клиент может подменить представление приложения о схеме запроса. Настройки cookies, HTTPS redirect и HSTS должны соответствовать реальному TLS-маршруту; не отключайте их ради прохождения healthcheck через внешний адрес.

## Первый запуск и обновление

Production Compose не использует bind mounts кода приложения или reload; отдельный SQL-файл монтируется только для инициализации ролей PostgreSQL. PostgreSQL и Redis доступны во внутренней сети Compose; API публикуется на loopback для reverse proxy на том же сервере.

Перед обновлением остановите upstream ingestion и все старые экземпляры приложения, включая другие Compose-проекты, процессы и реплики. Миграция `0003` меняет контракт записи и не должна выполняться параллельно с прежним бинарником. `make production-up` останавливает только web-сервис этого Compose-проекта; остальные писатели должны быть остановлены оператором.

```bash
docker compose -f docker-compose.production.yml build web release
docker compose -f docker-compose.production.yml up -d postgres redis
docker compose -f docker-compose.production.yml stop web
docker compose -f docker-compose.production.yml run --rm release python manage.py validate_trade_data
docker compose -f docker-compose.production.yml run --rm release python manage.py migrate --noinput
docker compose -f docker-compose.production.yml run --rm release python manage.py collectstatic --noinput
docker compose -f docker-compose.production.yml run --rm web python manage.py check --deploy
docker compose -f docker-compose.production.yml up -d web
```

На пустом PostgreSQL volume bootstrap-скрипт создаёт две разные роли без SUPERUSER (имена должны отличаться друг от друга и от `postgres`): runtime-приложение получает DML, release-роль владеет таблицами и выполняет миграции. Административные и migration-секреты не должны попадать в окружение web-контейнера. Runtime-процесс не выполняет DDL. Записи `Trade` в Django admin доступны только для чтения; создание и изменение событий проходят через ingestion.

Для существующего volume init-скрипты PostgreSQL повторно не выполняются. Перед переходом на разделённые роли требуется проверенное DBA provisioning: создать роли, проверить владельца схемы/таблиц, текущие и default privileges и протестировать release и web на копии. Простая замена паролей в `.env` не меняет пароли существующих PostgreSQL-ролей. Не удаляйте production volume для применения init-скрипта.

Если preflight или миграция завершается ошибкой, `make production-up` намеренно оставляет web остановленным. Сначала установите причину и состояние схемы; не возвращайте старый бинарник к записи без проверки совместимости. Возобновляйте upstream ingestion только после успешной проверки новой версии.

Перед обновлением действующей БД выполните backup и репетицию миграций на восстановленной копии.

`validate_trade_data` проверяет legacy-данные перед наложением новых ограничений; на новой БД отсутствие торговой таблицы не должно требовать ручного создания таблицы. Миграции выполняются отдельно от старта web-контейнера; entrypoint не изменяет схему автоматически.

Внешняя проверка после release:

- `/health/live/` — процесс отвечает; endpoint не проверяет БД.
- `/health/ready/` — подключены БД и кэш; при отказе зависимости возвращается 503.
- Авторизованный запрос с новым уникальным `trade_id` — 201; идентичный повтор — 200.
- Запрос без токена — 401; неверные денежные значения — 422.

Встроенный container probe подключается к loopback и использует первый корректный `ALLOWED_HOSTS` как `Host`, поэтому добавлять `localhost` только ради него не требуется. Для собственных readiness probes используйте разрешённый `Host` без wildcard. Проверьте startup timeout, логи и состояние БД при отказе старта; бесконечное ожидание зависимости не используется. Не запускайте production под `manage.py runserver`.

## Миграция legacy-данных

Переход добавляет `notional` и `quote_currency`, заполняет стоимость как точное произведение цены и количества и вводит ограничения БД. Существующее поле `pnl` сохраняется как legacy-данные; новый API его не возвращает и не заполняет. Историческая оценка риска не пересчитывается автоматически.

Неконечные/неположительные цены или количества и risk score вне диапазона 0–100 требуют исправления до миграции. Не подменяйте такие записи нулями или случайными значениями: восстановите их по первичному источнику либо согласуйте отдельный процесс обработки ошибочных событий.

Транзакционная миграция данных может блокировать или переписывать таблицу; для большой базы нужно окно обслуживания и измерение длительности на копии. Отдельная миграция индекса использует concurrent creation, но это не обещание отсутствия любых блокировок при всём обновлении.

Откат схемы не равен откату образа. Новая уникальность `(exchange_id, trade_id)` допускает одинаковый `trade_id` разных бирж; возврат к прежней глобальной уникальности может не пройти. До downgrade выполните `docker compose -f docker-compose.production.yml run --rm release python manage.py validate_trade_data --check-downgrade`, проверьте совместимость кода и восстановление backup. Не выполняйте автоматический downgrade после появления новых событий без проверенного плана.

## Ротация сервисных токенов

1. Создайте новый случайный секрет и добавьте его в `INGEST_API_TOKENS` под временным отдельным именем клиента, сохранив старый ключ на короткое окно перехода. Учитывайте, что отдельное имя получает отдельную квоту.
2. Перезапустите экземпляры приложения с новой конфигурацией, затем переведите отправителя на новый токен. Не отправляйте секрет через журналы или issue/PR.
3. Проверьте приём событий, удалите старую запись и повторно обновите экземпляры приложения. Старый токен должен получать 401.

При компрометации удаляйте ключ немедленно и разбирайте подозрительные события по идентификаторам. Токен не шифрует трафик: требуется HTTPS. Ротация Django `SECRET_KEY` затрагивает сессии и подписи и выполняется отдельно.

## Резервное копирование и восстановление

Храните backup вне хоста приложения с ограниченным доступом, шифрованием и сроком хранения. Пример дампа без вывода пароля:

```bash
docker compose -f docker-compose.production.yml exec -T postgres \
  sh -c 'PGPASSWORD="$POSTGRES_PASSWORD" pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' \
  > novatrade-backup.dump
docker compose -f docker-compose.production.yml exec -T postgres pg_restore --list < novatrade-backup.dump
```

Сначала восстановите дамп в отдельную тестовую PostgreSQL и проверьте число записей, ограничения, миграции и повтор ingestion. Выполняйте восстановление production только в согласованном окне с остановкой записи и проверенным переключением; команды автоматического удаления БД/томов не входят в workflow. Периодически измеряйте RPO/RTO на реальном восстановлении.

## Нагрузочные измерения

Установите группу `load`: `uv sync --frozen --group load`. Запускайте нагрузку только на предназначенном для этого окружении. `BENCHMARK_TOKEN` передавайте через окружение из secret manager или безопасного ввода; не вставляйте значение в командную строку. Для локального запуска скрипт также читает `INGEST_API_TOKENS` из `.env` и выбирает `local-ingestor` (или имя из `--token-client`).

```bash
make benchmark BENCHMARK_HOST=http://127.0.0.1:8000
```

Уточняйте доступные параметры через `uv run --frozen --group load python scripts/benchmark.py --help`. Скрипт сохраняет конфигурацию нагрузки и сводку отдельно от секретов. Включайте в результат версию кода, время прогона, число клиентов, длительность, конфигурацию ресурсов, успешные RPS, долю ошибок и p95/p99 успешных запросов. По умолчанию результат записывается в новую папку `work/benchmarks/<UTC timestamp>/`: `report.json`, `measurements.json`, Locust CSV и журнал. Время измерения включает разгон; metadata фиксирует commit и признак изменённой рабочей копии. При сравнении меняйте один существенный параметр за раз.

По умолчанию проверяется наличие успешных запросов и доля ошибок не выше 1%; минимальные RPS и максимальная p95 не заданы. Для проверки SLO задайте `--min-success-rps` и `--max-p95-ms`; `--max-error-rate` меняет бюджет ошибок. Прохождение настроек по умолчанию не подтверждает целевую пропускную способность.

Квота ingestion действует и во время benchmark. Для измерения пропускной способности назначьте тестовому клиенту соответствующую квоту в изолированном окружении; не отключайте защиту production. Сначала проверьте корректность ответа и идемпотентность, затем измеряйте CPU, I/O, число соединений БД, блокировки и планы запросов. Общие RPS с большим числом отказов не являются успешной пропускной способностью.

Исторический Locust CSV с 46,98% ошибок описывает предыдущую реализацию. Сравнение с ним требует учёта отсутствующих метаданных и неизвестных причин ошибок; он не является baseline успешной работы.
